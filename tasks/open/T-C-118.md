# T-C-118 — Grade commit carries the instructor's final scores and closing comment

**Workstream:** integration  (contract changes are never claimed by builder workstreams)
**Size:** S
**Opened by:** engine (Round 2 Phase 2, from T-E-114)
**Status:** applied on round2/phase2, awaiting approval
**Blocks:** T-E-114 acceptance items 1 and 3 on the server side (the engine side is done on round2/phase2)

## What needs to change
- `contracts/mcp-tools.md`: `assessments.commit_grade` input gains the instructor's inputs;
  `assessments.draft_grade` notes that it writes `criterion_scores.ai_score`.
- `contracts/api.openapi.yaml`: `POST /api/approval` documents the `grade_commit` edit.
- `contracts/events.md`: the `grade_commit` approval preview documents `artifact.requires`.

## Why it's needed
spec.md §7.4 says `commit_grade` requires the instructor's `final_score` on every criterion
and a non-empty `holistic_md`, and mcp-tools.md already says the server errors without them.
But no served tool writes `criterion_scores.final_score`, and `commit_grade` takes only
`{ grade_id }`, so the instructor's scores have nowhere to go. `draft_grade` also writes only
`grades`, never `criterion_scores.ai_score` (§7.4).

The engine (T-E-114, round2/phase2) now requires the approver's edit to carry
`final_scores` for every criterion and a non-empty `holistic_md` (422 from
`POST /api/approval` otherwise, and the gateway refuses on resume), drops any the model
proposed, records the per-criterion diff in `human_decisions`, and passes the three fields
to `commit_grade`. Today's server ignores them, so `grades.scores` stays the AI's draft and
no `final_score` is written.

## Proposed change (draft)
### `assessments.commit_grade` (mcp-tools.md)
- Input: `{ grade_id: string, final_scores: object, holistic_md: string, feedback?: object }`
- Notes: `final_scores` maps each criterion key of the grade's rubric to the instructor's
  whole-number score; `feedback` maps criterion keys to the instructor's edited text
  (unnamed criteria keep the draft's). The engine sets all three from the approver's edit and
  never from the model. In one transaction the server writes `criterion_scores.final_score`
  for each criterion (upsert on `(submission_id, criterion_id)`), sets `grades.scores` to
  `final_scores`, `grades.holistic_md`, merges `feedback`, then commits. `validation_error`
  when a rubric criterion has no score, a score is not one of the criterion's level scores,
  or `holistic_md` is blank; `conflict` when already committed.

### `assessments.draft_grade` (mcp-tools.md)
- Notes (add): for a submission whose assignment has `rubric_criteria`, also upserts
  `criterion_scores.ai_score` (and `ai_rationale` from `feedback`) for each scored criterion;
  never `final_score` or `released_at`.

### `POST /api/approval` (api.openapi.yaml, description)
For `artifact_type: grade_commit` the decision must be `edit`, and `edited_payload` is
`{ grade_id, final_scores: { <criterion key>: integer }, holistic_md: string,
feedback?: { <criterion key>: string } }`. `final_scores` must cover every key in the
preview's `artifact.requires.final_scores`; otherwise, or with a blank `holistic_md`, the
response is 422 and the approval stays pending.

### `approval_request` (events.md)
For `grade_commit`, `preview.artifact.requires = { final_scores: string[], holistic_md: true }`
lists the criterion keys the approver must score.
