# T-C-119 — Feedback runs that fail are visible and can be retried

**Workstream:** integration  (contract changes are never claimed by builder workstreams)
**Size:** S
**Opened by:** engine (Round 2 Phase 2, review of T-D-104)
**Status:** applied on round2/phase2, awaiting approval

## What needs to change
- `contracts/api.openapi.yaml`: `FeedbackStatus` gains `failed`; new
  `POST /api/feedback/{submission_id}/retry`; the release 409 mentions failed generation.
- `contracts/events.md`: `feedback_ready` polling stops at `released`, `suppressed` or `failed`.

## Why it's needed
Draft feedback is generated in the background. When the feedback agent errors or saves
nothing, the submission stayed `pending` forever: the instructor's release returned 409 "no
feedback yet", nothing retried, and clients told to poll until `released` polled forever.

## Change (as applied)
- When a run saves no criterion feedback (agent error, nothing saved, no rubric), the engine
  writes a `criterion_feedback` ai_actions row for the submission (`target_type
  submissions`, `output = {submission_id, failed: true, reason}`). Feedback status is
  `failed` while the submission has no recorded feedback and such a row has no `dismissed`
  decision.
- Under `auto` release, when the feedback was saved but `assessments.release_feedback`
  refused the release, the engine writes the same row with `reason: release_failed`, and the
  status is `failed` (not `awaiting_release`) until the row is dismissed. A retry keeps the
  saved feedback and only re-attempts the release.
- `POST /api/feedback/{submission_id}/retry` (submitter with `submit_work`, or faculty of the
  course with `feedback_release`): 409 unless `failed`; records `dismissed` by the caller on
  each failed run, starts a new run, returns 202 with the caller's SubmissionFeedback
  (`status: pending`).
- Failed runs never reach the learner's ai-actions log and are left out of AI Review rates.

## Impact
- Workstreams affected: frontend (show `failed` and a Retry button on both UIs' feedback
  views; stop polling on `failed`), data-mcp (none; the row is engine-written).
- Breaking change: an added enum value; clients switching on FeedbackStatus need a branch.
- Migration needed: no.
