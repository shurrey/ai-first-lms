# T-E-131 — Object-level checks for tools keyed by submission_id or session_id

**Workstream:** engine
**Phase:** 1 (spec.md §19.1)
**Size:** M
**Status:** open
**Spec:** spec.md §4.4, §4.5, §5.2 step 3, §17
**Dependencies:** T-E-106

## Goal
The tool gateway scope-checks `person_id`, `student_id` and `course_id` only. Tools keyed by another id get no object-level check, so a faculty member using grading_assistant can read any submission by id.

## Context
- Affected today: `assessments.get_submission`, `assessments.commit_grade` (and an approver's edited `submission_id`), `roster.get_session_transcript`, and any tool whose only subject key is `submission_id` or `session_id`.
- Students cannot reach these agents, so nothing regresses; the gap is staff reading outside their courses.
- Align `assessments.approve_credential` approver coverage on the agent write-gate path with the REST rule (faculty of the course, or admin) when the §17 role tightening lands; today `_covers_course` also lets an advisor approve for a course containing an advisee.

## Acceptance criteria
- [ ] The gateway resolves `submission_id` → (student, course) and `session_id` → (person, course) through the scope directory and applies `scope.can_view_student` before executing.
- [ ] An approver's edited arguments are re-resolved and re-checked on resume.
- [ ] A denial is a `denied_scope` tool result and a `guardrail` event.

## Tests required
- Gateway unit tests with fakes: faculty of another course gets `denied_scope` for a submission and a session transcript; own course passes.
