## Why it's needed
`assessments.propose_alignment` is read-only and its contract says accepting a proposal sets
`rubric_criteria.outcome_nodes` "through the engine endpoint that records the
`human_decisions` row". The engine does not write `rubric_criteria` (data access goes through
MCP tools), and no served tool writes it, so an accepted alignment cannot be stored.

## Proposed change (draft)
### `assessments.apply_alignment`
- Mutates: true. Requires approval: true (a model-initiated call suspends; the engine
  endpoint that calls it on the instructor's click records them as `approved_by`).
- Allowed roles: `faculty` (own courses), `instructional_designer`
- Input: `{ assignment_node: string, criteria: [{ key, description, levels: [{ score, label,
  descriptor }], outcome_nodes: string[] }], reviewer_id: string }`
- Output: `{ rubric_id, criterion_ids: string[], created: integer, updated: integer }`
- Notes: Validates exactly as `propose_alignment` does (3–6 criteria, outcomes of the course).
  Creates the assignment's rubric when it has none (sets `nodes.metadata.rubric_id`), upserts
  `rubric_criteria` on `(rubric_id, key)`, and adds `aligned_with` edges from the assignment
  to each outcome. Refuses (`conflict`) to change a criterion that already has scores.
  The engine writes one `human_decisions` row per proposed criterion (accepted / edited /
  rejected) on the proposal's `ai_actions` row.

## Applied (2026-10-03, branch round2/phase2 (engine lane)) — awaiting approval
- `contracts/api.openapi.yaml`: new `POST /api/assignments/{assignment_node}/alignment/decisions`
  (`decideAlignment`) and schema `AlignedCriterion`.
  - Course faculty only (`taught_course_ids` contains the assignment's `metadata.course_id`); 403
    otherwise, admin and program_lead included.
  - Body: `{ ai_action_id?: uuid, decisions: [{ key, decision: accept | edit | reject,
    criterion?: AlignedCriterion (required for edit), reason? }] }`, 1–6 decisions, one per
    proposed key. `ai_action_id` defaults to the assignment's latest proposal.
  - The proposal is a `generation` ai_actions row the provenance recorder now writes for each
    successful `assessments.propose_alignment` call that returns a `proposal` (target_type
    `nodes`, target_id the assignment, output `{ tool, assignment_node, proposal }`, sources the
    assignment node and syllabus).
  - Accepted (as proposed) and edited (as given) criteria go to `assessments.apply_alignment` in one
    call with the caller as `requester_id`; nothing is recorded when it refuses (404 / 409 / 422,
    else 502). Rejecting every criterion calls no tool.
  - Each proposed key is decided once: a request naming a key that already has a decision on the
    proposal is 409 before any write. An edited `criterion.key` must equal the choice's `key`
    (422).
  - Then one `human_decisions` row per choice on the proposal: `accepted` (diff
    `{criterion_key}`), `edited` (diff `{criterion_key, fields: {name: {before, after}}, changed}`),
    `rejected` (diff `{criterion_key}`), with the choice's `reason`.
  - Response 201: `{ ai_action_id, assignment_node, rubric_id (null when all rejected),
    criterion_ids, decisions: HumanDecision[] }`.
- Engine: `src/engine/api/alignment.py`, `src/engine/provenance.py` (`_alignment_proposed`); tests
  `src/engine/tests/test_alignment_practice_api.py` and, against Postgres and the real handler,
  `src/engine/tests/integration/test_alignment_practice_db.py`.
