# T-E-106 — ToolGateway steps 1–3, 7, 10 + manifest-driven tools

**Workstream:** engine

**Size:** L
**Status:** open
**Spec:** spec.md §5.2, §4.5, §5.5
**Dependencies:** T-C-100, T-C-104, T-E-098, T-E-103

## Goal
Route every live tool call through one gateway that reads tool lists from the manifests.

## Context
- New `engine/guardrails/gateway.py::ToolGateway.invoke(ctx, agent, tool, args) -> ToolResult`, called from `_tool_loop` instead of MCP directly.
- This generalizes the S5 plumbing (T-E-098); there must not be a second guardrail path.

## Acceptance criteria
Copied from spec.md; the source section is in parentheses after each item.
- [ ] Step 1 allow-list: the tool must be in the agent's manifest `tools`; `_AGENT_TOOLS` is deleted and the runner reads `contracts/agent-manifests.yaml` via `engine/manifests.py` (§5.2).
- [ ] Step 2 permission: `permissions.check(ctx.active_role, tool.allowed_roles)` from `mcp-tools.md` metadata (§5.2).
- [ ] Step 3 identity and scope: `person_id`/`student_id`/`requester_id` forced to self for students; checked with `scope.can_view_student` for faculty/advisor/admin; denials raise `ScopeDenied`, return a "not permitted" tool error and emit a `guardrail` event (§5.2, §4.5).
- [ ] Step 7 executes the MCP call; step 10 writes a `tool_calls` record (§5.2; table from T-D-102).
- [ ] The agent context prefix includes `requester: {display_name, active_role}` (§4.5).
- [ ] `grep -R "_AGENT_TOOLS" src/` returns nothing (§5.5).
- [ ] A student-role session cannot invoke `assessments.commit_grade` even if the prompt asks (§5.5).
- [ ] A tutor prompt "show me Noah Brown's mastery" from Emma results in no Noah data, and the tool gateway logs a scope denial (§4.8).
